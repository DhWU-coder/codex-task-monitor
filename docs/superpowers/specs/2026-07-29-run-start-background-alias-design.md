# Run 与 Start 后台别名设计

## 1. 背景

当前 `codex-task-monitor run` 会在终端前台阻塞运行，而 `start` 会创建独立后台进程。用户确认两条命令都应后台运行，并且行为完全等价。

## 2. 目标行为

- `codex-task-monitor run` 和 `codex-task-monitor start` 都调用同一后台启动流程。
- 两条命令都在健康检查通过后返回终端并打印实际 UI 地址。
- 服务已经运行时，两条命令都不创建第二个进程，打印“监控器已在运行”和当前 UI 地址。
- 后台启动失败时，两条命令都打印相同错误并以非零状态退出。
- `stop` 和 `restart` 行为保持不变。
- 隐藏命令 `_serve` 继续作为后台子进程内部使用的前台阻塞入口。

## 3. 实现方案

在 `codex_task_monitor/cli.py` 中提取一个不注册为 CLI 命令的共享函数，负责：

1. 加载稳定配置。
2. 调用 `_start_background`。
3. 统一处理 `RuntimeError`。
4. 根据 `already_running` 输出状态。
5. 打印 UI 地址。

`run_command` 和 `start_command` 只保留各自的 Typer 命令注册与帮助文本，然后调用该共享函数。这样可以保证两条命令以后不会因复制逻辑而产生行为差异。

`_run_foreground` 不删除，因为 `_serve` 仍需使用它运行 Uvicorn；仅修改 `_serve` 的说明，使其明确供 `run` 和 `start` 创建的后台进程调用。

## 4. 文档调整

README 的 CLI 章节不再把 `run` 描述为前台命令，而是说明：

- `run`：后台启动，与 `start` 等价。
- `start`：后台启动，与 `run` 等价。
- 两者均幂等并打印 UI 地址。

新增设计文档作为对初始设计中“run 前台运行”要求的后续修订；历史实施计划不重写。

## 5. 测试

- 修改现有 `run` 命令测试，断言它调用 `_start_background` 而不是 `_run_foreground`。
- 参数化验证 `run` 和 `start` 都输出后台启动结果及 UI 地址。
- 参数化验证服务已运行时两条命令都输出相同提示，且底层幂等逻辑不创建第二个进程。
- 参数化验证后台启动失败时两条命令都返回退出码 `1`。
- 运行完整 Python 测试、Ruff 和 mypy；本次不修改前端，但仍运行前端测试、类型检查与构建作为回归验证。

## 6. 运行中服务保护

实现和自动化测试不停止、不重启当前正在运行的监控器。代码通过可编辑安装立即可见，但现有后台进程只有在用户下次主动执行 `restart` 后才会加载新代码。
